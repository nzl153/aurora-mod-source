## 1. 地基：热量为什么是这样

整个卡池只有一个核心张力：**打得越狠，离自燃越近。**

热量不是资源条，是**风险条**。它跟大部分卡牌游戏的资源不同：

- 它**没有「花掉」的动作**。不能主动消耗热量换收益，只能被动承受它带来的增伤和过热。
- 它**只有一个方向是好的**（进过载区拿 ×1.25），而这个方向同时把你推向过热。
- **散热是止损，不是收益**。

这个设计要让玩家每回合都做同一个判断：这一刀值不值得让炉温再涨一格。
改热量系统之前先问：改完之后，「要不要再打一张」这个问题还紧张吗？不紧张了就是改坏了。

**过热的具体机制**（逐步迭代出来的，别轻易动）：

- 热量到 10 → **锁定**一笔过热伤害（记在 `AuroraLockedOverheatDamagePower`），回合结束时受到，可格挡
- 锁定之后**散热不能抹掉这笔债**——这是刻意的。否则「冲到 10 再散回去」就是无代价白嫖增伤
- 过热次数越多伤害越高（10/12/14/16），防止无脑循环过热
- **战斗胜利则免除**——打死最后一个敌人的那一刀不该反杀自己。这是体验妥协，不是漏洞

## 2. 四条流派各自解决什么问题

一个角色的流派不该是「四种不同的加数字方式」，得各自回答一个不同的问题。

### A · 过热暴走（主轴，58 张卡带热量标签）

**回答的问题**：我愿意为伤害付出多少血？

默认玩法，也是唯一一条「不需要凑组件就能走」的路。主动冲红线、吃自伤、换爆发。
关键卡：超频（把过热代价从掉血改成掉最大生命，换 +75%/层）、极限断裂（本场自损累计转伤害）、
葬炉 / 炉心淬锋（过热存活后拿力量 / 剑势）。

**为什么它卡最多**：因为热量是所有卡都要面对的东西，不带热量标签的卡反而是少数。
这不代表其他三条是配角。

### B · 剑势（18 张）

**回答的问题**：我是现在就打，还是再等一回合？

剑势是**无上限、不衰减**的计数器。它经历过一次重大修正，值得记录：

> **早期版本里剑势本身没有任何被动效果。** 它是个纯存钱罐——在抽到稀有兑现口
> （一刀两断 / 无月）之前，收益恒为 0。这就是「剑势从来没用出来过」的根因：
> 不是数值低，是**在兑现之前它什么都不是**。

后来加了被动底薪：每 3 点剑势使攻击 +1，最多 +5。**注意只封被动这一段，计数本身仍然无上限**，
所以一刀两断那种倾泻口的天花板完全没受影响。

这个改动的副作用比主作用更重要：**它让「清空」第一次有了代价**。
在那之前清空剑势是纯收益（反正留着也没用）；之后，清空 20 点 = 换爆发但失去后续每刀 +5。
一刀两断（清空）和无月（不清空）从此成了真的抉择。

### C · 悬浮模块（攻击 / 护盾各 19 张）

**回答的问题**：我这两个格子放什么？

模块是**唯一有「场面」概念**的流派——部署在场上、自动触发、可以强化、可以轮转类型。
基础 2 槽、硬上限 3，满槽再部署必须替换一枚。

**槽位少是刻意的**。给到 5 个槽，这条流派就变成「堆满就赢」，取舍消失。2→3 的紧张感才是它的乐趣。

**退役激发**：满槽替换时，**被替换的那一枚离场前按当前强化值触发一次**。
对齐原版充能球「被挤出时激发」的语义——满槽替换不再是纯粹的损失，而是「打完最后一发再退役」。
取舍本身没有削弱：依然失去了一枚可能强化很久的模块，只是拿回一次触发当退役金。

⚠️ 只有**满槽替换**这一条路径激发。**轮转**（`RotateAsync`，模块换型不算离场）和
**收回**（`Recall*`，玩家主动拆械、通常已另有收益）都不激发，别顺手加上去。
实现在 `AuroraModuleController.DeployAsync`，必须在 `PowerCmd.Remove` **之前**调
——Remove 之后 `Owner` 已置空，攻击模块取不到 `CombatState` 会静默失效。

模块伤害走 **Unpowered**，所以**不吃过载 ×1.25、不吃剑势底薪**。
这是防止「模块数 × 热量 × 剑势」三轴指数爆炸的关键闸门，**绝对不要改**。

### D · 指令连锁（17 张）

**回答的问题**：我这回合的出牌顺序对不对？

每回合手动打出第 3 张牌时激活，持续到回合结束。自动打出、复制结算、额外结算都不计数
——**只认玩家的手动操作**，这是为了让它真的考验出牌规划，而不是被 Echo 之类的效果白嫖。

### 配套机制：锁定 与 挑战协议

这两个不是独立流派，是**给 C 和 B 提供互动的粘合剂**：

- **锁定**：给敌人上 debuff，你的攻击和攻击模块每命中一段消耗 1 层、追加 2 点平伤。
  它让攻击模块有了「打谁」的智能（优先打锁定最高的敌人）。
- **挑战协议**：给敌人上 **buff**（所以人工制品挡不住），让它对你造成的伤害 +10%/层。
  **主动加大自己承受的风险，再用专门的卡把这份风险兑现成收益。**

挑战协议后来并入了剑势流派（挑衅、协议破坏者、反制姿态都给剑势），
因为它单独撑不起一条线，但作为「风险→剑势」的转换器很合适。

## 3. 数值是怎么定的（改数值前必读）

**基准来源不是感觉，是原版的 680 张卡。**

解包出的原版源码里，`localization/` 下有各语言的官方文案。
调平衡、对齐文案体裁，一律拿它当基准。

具体做法：把本 mod 每个「稀有度 × 费用」格子的攻击 / 格挡中位数，跟原版同格子的中位数对比。
有一轮就是这么发现 **1 费罕见位是唯一的洼地**（攻击中位数 7 vs 原版 8，格挡 6 vs 7），
而 2 费档反而普遍高出一档。于是精确补了 5 张 1 费罕见各 +1，其他一律不动。

**以后再调数值，用同一套方法**：先统计原版对应格子的中位数，再看本 mod 偏在哪儿，
只补真正的洼地。不要凭手感整体上调。

**当前评估**：数值健康，强度不超标，各档位基本贴合原版基准。

## 4. 刻意为之，不是 bug

这一节的存在意义：**防止把设计「修」掉。**

| 现象 | 这是刻意的，因为 |
|---|---|
| 模块伤害不吃过载增伤、不吃剑势底薪 | 防三轴指数爆炸。见 §2C |
| 散热不能减少已锁定的过热伤害 | 否则「冲 10 再散回」= 无代价白嫖增伤 |
| 剑势被动封顶 +5，但计数无上限 | 只封被动，倾泻口天花板不受影响。见 §2B |
| 挑战反斩「先移除协议再攻击」 | 协议乘区**就是这张卡要兑现的东西**。若改成先打后移除，3 层会既吃 ×1.3 又吃 +18，双重计算 |
| 战斗胜利免除过热伤害 / 最大生命代价 | 收尾那一刀不该反杀自己 |
| 挑衅按「实际新增层数」给剑势 | 敌人已满 3 层时再上协议不给剑势，防刷 |
| 有些卡故意不强 | 卡池要有梯度。**不是每张卡都该是构筑核心**，但每张卡都得在某个局面有用 |
| 一刀两断「读快照 → 攻击 → 再清空」 | 见 §6，这个顺序不能反 |
| 装甲冲撞**不消耗**格挡 | 与原版全身撞击一致。消耗的话它就成了「一次性把乌龟本钱烧光」，反而逼玩家更保守 |
| 冗余装甲只保留**一半**，不是全留 | 全留 + 装甲冲撞 = 一代 Barricade + Body Slam 无限。保留一半数学上收敛到 2× 每回合产出，有界 |
| 泄势斩的剑势追加段**封顶 12**，且不清空剑势 | 不封顶时 1 费罕见会打出超过稀有兑现口的数字。只封本卡追加段，剑势计数与底薪不受影响 |
| 泄势斩**不消耗**剑势 | 剑势只支持「清空全部」，刻意无 Spend(N)。要做部分消费得先改架构，别顺手加 |

## 5. 常见反馈怎么应对

### 「某张卡太强 / 太弱」

1. **先问是在什么局面下感觉到的**——单卡强度和构筑成型度是两回事。
   剑势卡在没成型时都显得弱，这是设计而非缺陷。
2. **查原版同「稀有度 × 费用」格子的中位数**（§3），确认是真偏离还是感觉问题。
3. 要改的话，**遵守稀有度铁律**（§7 第 1 条）。

### 「某流派没存在感」

这个反馈要认真对待——剑势就是这么被发现有问题的。但**先区分两种情况**：

- **卡不够多 / 前中期没有兑现口** → 补卡或调整现有卡的定位
- **机制本身没有即时收益** → 这是根本问题，得给它一个「攒的过程中就有回报」的东西
  （剑势底薪就是解法）

第二种远比第一种严重，因为再多卡也救不了一个「兑现前收益为 0」的机制。

### 「多人联机出问题」

先看 §6 的联机注意事项。本 mod 的联机安全性是审过的：无随机源、归属用 NetId、
10 个能力有断线重连守卫。真出问题优先怀疑**新加的代码**是否违反了那几条。

## 6. 引擎硬知识（改代码前必读）

### 联机安全

- **绝对不要**在代码里用 `Random` / `DateTime` / `Guid` / `Time.Get*`。目前全库零使用，保持住。
- **归属身份一律用 `AuroraPerApplier`（NetId）**，绝不拿裸 `Creature` 引用当字典键。
- 「每场 / 每回合一次」的效果必须用持久化标记（`AuroraTurnGatePower` 等），
  否则**断线重连会二次触发**。

### 卡牌预览（`AuroraScalingDamageVar`）

- 联机同步的卡牌字段只有 `{Id, 升级等级, 附魔, SavedProperties, 入队楼层}`。
  **`PreviewValue` 物理上不进校验和，写它不可能 desync；写 `BaseValue` 会。**
- 目前全库 `PreviewValue` 只有一个写入点，就是这个类。保持这样。
- 它是原版 `DamageVar.UpdateCardPreview` 的忠实复刻，
  连「钩子覆盖附魔累加值」这个怪异行为都照抄了（原版就这样，保持一致才对）。
- 已接 6 张卡。**裂芯斩 / 湮灭指令是多段攻击，按原版惯例显示每段，故意不接。**

### canonical 卡（图鉴 / 主菜单里的模板卡）

- `card.CombatState` / `card.RunState` 在 canonical 下**安全返回 null**
- `card.Owner` 会**抛 `CanonicalModelException`**，直接崩百科
- 所以任何读战斗状态的预览逻辑，**先判 `CombatState == null`**，再套 try/catch 兜底

### ⭐ 结算顺序陷阱（最难查的一类 bug）

影响己方输出的隐式钩子**只有四个**，各自读的状态是：

| 钩子 | 读什么 |
|---|---|
| `AuroraSystemCrashPenaltyPower` | 手牌里有没有宕机牌 |
| `ChallengeProtocolPower` | **目标身上**由你施加的协议层数 |
| `HeatPower` | 己方热量区段 + 过热 pending + 超频层数 |
| `MomentumPower` | 己方剑势 |

**规则：如果一张卡在攻击结算之前修改了这四样中的任何一样，那份变化会影响这次攻击。**

这就是一刀两断那个 bug 的成因——它原本「先清空剑势再攻击」，
导致剑势底薪在攻击瞬间读到 0，20 势时实际打 88 但卡面预览 93，
而且这份损失玩家完全看不见（攒得越多亏得越多的隐形陷阱）。

**排查同类问题时，只需要检查这四项**，不用全库扫。
目前全库只有两张卡在攻击前动状态，都已验证安全：
拆械斩（模块数不进任何钩子，且强化量已提前读好）、挑战反斩（设计意图，见 §4）。

⚠️ **这类 bug 静态审查发现不了，只有实机能撞见。**
以后加「消耗某资源换伤害」的卡，务必手动检查这一条。

## 7. 改动铁律（碰了会连锁出事）

### 1. 稀有度总数不可变

各稀有度的卡牌数量是固定的。要动某张卡的稀有度，**必须 1 对 1 对调**：
升上去的加强、降下来的削弱。不能单方面挪。

### 2. 代码里的数值不要写 `private const`，用 `DynamicVar`

**这条是血的教训。** 剑势共鸣的阈值从 6 改成 10 时，只改了 `cards.json`、漏了 `powers.json`，
悬停一直显示 `<6`，直到实机才发现。同类问题在三相指令核也出现过。

改成 `DynamicVar` 之后，文案用占位符 `{Threshold}` 自动追踪，这类漏改在源头消失。
**新写代码时直接用 `DynamicVar`，别图省事写 const。**

### 3. 模块伤害必须保持 Unpowered

见 §2C。这是防指数爆炸的闸门。

## 8. 构建

### 构建顺序（不能反）

**改了本地化或资源** → 必须先导 pck、再 build dll。
因为 headless Godot 导出会触发它自己的 C# 编译，把已部署的 dll 覆盖掉。

只改代码的话，build dll 就够了。

```bash
# 1. 导 pck（游戏必须完全退出）
godot --headless --path <项目路径> --export-pack "Windows Desktop" <输出路径>

# 2. build dll
git checkout HEAD -- AuroraMod.csproj AuroraMod.sln   # csproj 会被 Godot 改，先还原
STS2_GAME_DIR="<游戏安装目录>" dotnet build AuroraMod.csproj -c Debug
```

- 导出退出时报 `Attempt to unregister unexisting extension class 'Spine*'` 是**无害的**，忽略
- 构建应当是 **0 错误**。警告数取决于 BaseLib 版本，多出来的都要看一眼
- 游戏运行时 dll 复制会失败（文件被锁定），build 前先完全退出游戏

### beta 分支

**正式版与 beta 均已适配**（2026-08-17，beta `v0.111.0`）。
**一份源码 + 条件编译出两份 dll**，不复制源码目录——复制必然漂移（改了一边忘了另一边，这类 bug 极难查）。

```bash
dotnet build -p:Sts2Beta=true   # beta，定义 STS2_BETA
dotnet build                     # 正式版（默认）
```

差异全部收在 `#if STS2_BETA` 内。发布时同一个工坊 ID 挂两份构建，
靠 `minBranch` / `maxBranch` 让 Steam 按玩家所在分支自动派发。
⚠️ 上传顺序：**先给正式版那份钉 `maxBranch: "public"`，再传 beta 那份**。反过来会让正式版玩家集体加载失败。

| 3 | `CharacterModel.GenerateAnimator` 新增 `Creature` 参数 |
| 4 | `CreatureCmd.Damage` 删除 6 参数重载，改为末尾带 `CardPlay?` 的 7 参数版 |
| 5 | `CreatureCmd.LoseBlock` 只剩 `(ctx, target, amount, remover)` |
| 6 | `Hook.ModifyDamage` 在 `cardSource` 后插入 `CardPlay?` |
| 7 | `Hook.ModifyDamageInternal` 的 `combatState` 由 `CombatState` 改为接口 `ICombatState` |

第 4 条有个省事的地方：5 参数重载 `(ctx, target, amount, props, dealer)` **两个分支都有**，
所以 `cardSource` 为 null 的调用直接改用它即可，不必进 `#if`。

#### ⚠️ 三类「编译期发现不了」的坑

这三类都是 **0 警告 0 错误编译通过、运行时才暴露**，跨版本适配时要主动排查：

1. **Harmony 形参类型不匹配 → 启动即炸。**
   如第 7 条的 `ICombatState`，补丁形参不跟着改就抛 `HarmonyException`。
   而 `PatchAll` 是**一炸全停**：一个补丁挂不上，整个 mod 的补丁全部失效——
   游戏照常进、角色照常选，但功能全没了，很容易被误判成"至少没崩"。

2. **`[HarmonyPatch]` 里写死的参数类型数组不参与重载解析。**
   编译期不校验，启动时报 `Undefined target method`。`AuroraStrikeVfxPatch` 就是这么炸的。

3. **靠节点名找 UI → 静默失效。**
   这类补丁通常全程 `try/catch`（纯装饰，不该打断渲染），于是走错节点**既不抛异常也不打日志**，
   只表现为"效果看着没变"，比崩溃难查得多。卡框那次踩了三层：
   - `FindChild("Frame", recursive)` 是深度优先按名字扫，会**撞到另一个同名节点**；
     引擎自身用的是 `_frame = GetNode<TextureRect>("%Frame")`
     ⇒ **以反射读私有字段为准，名字查找降级为兜底**
   - beta 新增 `Model.FrameMaterial` 染色着色器，会盖掉自定义整图 ⇒ 置 `null`
     （正式版该处本就是 `null`，无副作用，故不进 `#if`）
   - beta 的 `UpdateVisuals` 会**再调一次 `UpdatePortrait()`** 把贴图刷回
     ⇒ 补丁要挂到 `UpdatePortrait`（`Reload` 与 `UpdateVisuals` 的共同末端）

   **定位方法**：这类问题别靠现象推理，直接临时打一行节点路径日志，一次定位干净。

#### 复测时最容易漏的三块

1. **预览路径**：`ModifyDamage*` 新增了 `CardPlay`，但浏览牌库 / 商店 / 战斗奖励 / 休息点升级时
   `cardPlay` 是 **null**，任何一处点了 `cardPlay.X` 就是空引用崩溃。
   测法：开局后只看牌库和商店，一张牌都不打就能测出来。
2. **存档往返**：改动若涉及 `SavedProperty`，键名没变 ≠ 读写还通。
   测法：叠层数 → 退主菜单 → 读档 → 看还在不在。
3. **Harmony 启动检查**：先看日志有没有 `HarmonyException`，再进战斗。

## 9. 文案规范

### 角色描述必须贴原版格式

原版的 character description 格式极死板：
**恰好两行、`\n` 换行、第一行纯身份（常常连动词都没有）、第二行纯打法，零抒情零排比。**

当前版本：

```
一台没有收到停机指令的战争机械。
战斗中不断推高炉温，用濒临过载的机体换取更重的一击。
```

### 写文案时的几个自查项

- **翻译腔**：「以热量作战」这类
- **三段式排比**：「越 X 越 Y，代价是 Z」
- **官腔列举**：「另有……三条路线」
- **开发内部术语泄漏到玩家可见文案**：债务 / 快照 / 门闩 / 兜底 / 序列化
  ——这些词玩家看不懂，已经清过一轮，写新文案时别再引入

### 条件加值伤害的文案惯例

原版有两种写法，本 mod **统一走模式 B**：

- 模式 A：`{InCombat:（造成{CalculatedDamage}点伤害）|}` 战斗中追加一行括号
- **模式 B（完美击）**：主数字直接是算完的最终值 + 一句加值规则说明

所以那 6 张卡的 `{Damage:diff()}` 显示的就是真实伤害，文案后半句只解释加值来源。
**不要再加「牌面数字为基础伤害」这类元说明**，那是没有预览功能时的补丁，已经删了。
